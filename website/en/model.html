A harness describes how agents, knowledge, checkpoints, and human decisions are organized. OHM gives that description a form: a YAML 1.2 document with the extension .ohm.

What is inside an .ohm file?

It is a single UTF-8 text document, not a ZIP archive or a language model. The normalized model has six main properties:

schemaVersion
Identifies the structural version declared by the document.
manifest
Harness identity: ID, name, version, description, declared license, and tags.
graph
The participants (nodes) and their connections (edges).
content
Embedded content: prompts, agents, skills, hooks, commands, and scripts.
runtime
Execution preference, CLI, environment variables, and secret references. Credentials should not be shared in the file.
validation
Validation metadata, including the declared simulation profile.

Your first file.

This example shows the adopted YAML syntax using structure version 1.0.0. The empty graph demonstrates the format; the multiline prompt illustrates authoring and is not executed. The desktop YAML reader is still being migrated. The license field is example metadata and does not declare the app's license.

hello.ohm
# OHM in YAML 1.2 — desktop support is being migrated.
schemaVersion: "1.0.0"
manifest:
  id: hello
  name: Hello
  version: "0.1.0"
  description: Minimal Open Harness Model example.
  license: MIT
  tags: []
graph:
  nodes: []
  edges: []
content:
  prompts:
    objective: |-
      Describe the objective of the work.
      Define the evidence required to accept the result.
  agents: {}
  skills: {}
  hooks: {}
  commands: {}
  scripts: {}
runtime:
  preferred: api
  cli: null
  env: []
  secrets: []
validation:
  mockProfile: default

A valid structure is the first step.

The project has a JSON Schema and a structural validator. JSON Schema will continue to validate data after YAML parsing: file syntax and model structure are separate decisions. The example on this page was checked against that structure after parsing the YAML.

Passing this check does not establish instruction quality, provider availability, script safety, or equivalent execution in another environment.

A concrete foundation. An evolving model.

OpenHarness already reads and exports JSON harness documents, represents graphs, and offers structural validation and simulation. The decision is to adopt YAML for .ohm files while keeping JSON in the APIs. The YAML reader and exporter implementation is pending. The migration should preserve support for older JSON files, including .oharness.

Connections still use IDs and edges. YAML anchors will not represent topology. Feedback loops and cycles need execution rules, limits, and cancellation; changing syntax does not address them.

Preserving all configuration on export, defining execution rules, and supporting other tools still require development and verification. Portability is a design commitment; each environment needs to implement the model and declare its limits.

OHM is an OpenHarness proposal. This page does not claim third-party standardization, universal compatibility, or independent governance.
